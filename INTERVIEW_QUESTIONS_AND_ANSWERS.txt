PART 2: PYTHON, DJANGO & DJANGO REST FRAMEWORK TECHNICAL QUESTIONS

Q2.1: "How does Django's `select_related` differ from `prefetch_related`, and 
      where did you apply them in this CRM?"
-----------------------------------------------------------------------------
Model Answer:
- `select_related()` performs an SQL `INNER JOIN` (or `LEFT OUTER JOIN`) and 
  retrieves related objects in a single database query. It is designed for 
  single-valued relationships: `ForeignKey` and `OneToOneField`.
  * In CRM Lite: Used on `Lead.objects.select_related('stage', 'assigned_to', 'created_by')`
    and `Customer.objects.select_related('lead', 'created_by')`.
- `prefetch_related()` executes a separate SQL query for the related set and 
  performs the join in Python memory. It is designed for multi-valued relationships: 
  `ManyToManyField` and reverse `ForeignKey` sets.
  * In CRM Lite: Used on `lead.notes`, `lead.follow_ups`, and `lead.calls`.
- Impact: Eliminates the N+1 query problem, dropping database roundtrips on lead 
  listing from 100+ queries to just 2 queries.

Q2.2: "How do you enforce object-level permissions in Django REST Framework?"
----------------------------------------------------------------------------
Model Answer:
"I implemented custom permission classes subclassing `rest_framework.permissions.BasePermission`:
  1. `has_permission(self, request, view)`: Evaluates global request conditions, 
     such as checking if the authenticated user has the `ADMIN` or `MANAGER` role.
  2. `has_object_permission(self, request, view, obj)`: Evaluates record ownership.
     For a Sales Executive:
     ```python
     if request.user.role == 'EXECUTIVE':
         return obj.assigned_to == request.user or obj.created_by == request.user
     return True
     ```
Crucially, I combine object permissions with `get_queryset()` filtering so 
unauthorized records are never returned in list queries in the first place."

Q2.3: "Why use Serializer validation over view validation?"
----------------------------------------------------------
Model Answer:
"DRF Serializers encapsulate data parsing, type coercion, and validation rules in 
a reusable, declarative layer:
  - Field-level validation (`validate_<field_name>`): Used to validate that 
    `expected_value >= 0` and verify phone number uniqueness on active leads.
  - Object-level validation (`validate(self, data)`): Used for cross-field rules, 
    such as mandating a non-empty `lost_reason` when `status` is transitioned to `LOST`.
This ensures identical validation whether data arrives via REST endpoints, 
management commands, or automated test runners."

Q2.4: "How does SimpleJWT handle token blacklisting and statelessness?"
-----------------------------------------------------------------------
Model Answer:
"JWT is intrinsically stateless: the server signs the payload with a secret key, 
and incoming requests are verified cryptographically without database hits.
To handle user logouts and revoked credentials, we use SimpleJWT's blacklist app.
When a user logs out, the frontend dispatches the refresh token to 
`/api/auth/logout/`, which writes the token's unique `jti` (JWT ID) claim into 
the database blacklist table. Future refresh requests with that token are rejected."

PART 3: RELATIONAL DATABASE ARCHITECTURE, TRANSACTIONS & ACID COMPLIANCE
================================================================================

Q3.1: "Explain ACID properties in the context of your Customer Conversion feature."
----------------------------------------------------------------------------------
Model Answer:
  - **Atomicity**: The creation of the `Customer` row, the update of `Lead.status` 
    to `WON`, the recording of `converted_at`, and the creation of an `ActivityLog` 
    are wrapped in `django.db.transaction.atomic()`. Either all four occur, or none do.
  - **Consistency**: Database constraints (unique `OneToOneField`, foreign key 
    integrity) guarantee that an invalid customer record cannot enter the database.
  - **Isolation**: Concurrent database transactions cannot view the intermediate 
    uncommitted state of a customer conversion until the commit is completed.
  - **Durability**: Once the transaction commits, the converted customer record 
    and audit log persist on disk, surviving power outages or server restarts.

Q3.2: "Why did you use `on_delete=models.PROTECT` on `Customer.lead` instead of `CASCADE`?"
-------------------------------------------------------------------------------------------
Model Answer:
"Using `models.CASCADE` would mean that deleting a Lead would silently delete the 
associated Customer and all invoicing/financial relationships. In an enterprise CRM, 
paying client accounts are legal and financial assets. `models.PROTECT` raises a 
`ProtectedError` if an admin attempts to delete a converted lead, guaranteeing 
audit preservation."

Q3.3: "What is your database indexing strategy and what trade-offs did you consider?"
------------------------------------------------------------------------------------
Model Answer:
"I added B-Tree indexes on:
  - `leads_lead(phone)` and `leads_lead(email)`: For sub-millisecond deduplication 
    and search lookups.
  - `leads_lead(status)`: For high-frequency Kanban pipeline grouping and KPI stats.
  - `leads_lead(assigned_to_id)`: For executive role isolation queries.
  - `followups_followup(follow_up_at, status)`: Composite index for instant overdue queries.
  - `activity_activitylog(entity_type, entity_id)`: For instant lead timeline loading.
*Trade-off*: Indexes accelerate `SELECT` queries by orders of magnitude (O(log N) 
instead of O(N) full-table scans) at the minor expense of additional disk storage 
and slightly slower `INSERT`/`UPDATE` operations due to index tree maintenance."

Q3.4: "How do you prevent race conditions when two users update the same lead simultaneously?"
---------------------------------------------------------------------------------------------
Model Answer:
"In high-concurrency environments, we use `select_for_update()` inside an atomic block:
```python
with transaction.atomic():
    lead = Lead.objects.select_for_update().get(pk=lead_id)
    # perform mutation
    lead.save()
```
This issues an SQL `SELECT ... FOR UPDATE`, placing an exclusive row-level lock 
on that lead until the transaction commits, preventing lost-update anomalies."

Q4.1: "How does the silent token refresh mechanism work in Axios?"
-----------------------------------------------------------------
Model Answer:
"In `frontend/src/api/axios.js`, I registered an Axios response interceptor:
```javascript
api.interceptors.response.use(
  (response) => response,
  async (error) => {
    const originalRequest = error.config;
    if (error.response?.status === 401 && !originalRequest._retry) {
      originalRequest._retry = true;
      try {
        const refresh = localStorage.getItem('refreshToken');
        const res = await axios.post('/api/auth/refresh/', { refresh });
        const newAccess = res.data.access;
        localStorage.setItem('accessToken', newAccess);
        originalRequest.headers['Authorization'] = `Bearer ${newAccess}`;
        return api(originalRequest); // Replay original request
      } catch (refreshErr) {
        localStorage.clear();
        window.location.href = '/login';
        return Promise.reject(refreshErr);
      }
    }
    return Promise.reject(error);
  }
);
```
This provides a completely seamless experience: users never experience jarring 
logouts when their 60-minute access token expires."

Q4.2: "Why use React Context API rather than Redux or Zustand for this application?"
-----------------------------------------------------------------------------------
Model Answer:
"For an enterprise CRM dashboard of this scale, global client state is primarily:
  1. Authentication state (`AuthContext` — user profile, role, login/logout).
  2. Notification / Toast state (`ToastContext` — transient alerts).
Server data (leads, stages, calls, follow-ups) is fetched on demand and scoped to 
specific pages. Introducing Redux would add substantial boilerplate (actions, 
reducers, thunks) without tangible benefits. React Context combined with modular 
API services (`leadApi`, `aiApi`, `followupApi`) provided clean separation, 
minimal memory overhead, and straightforward maintenance."

Q4.3: "How did you implement the visual Kanban board with responsive drag-and-drop?"
-----------------------------------------------------------------------------------
Model Answer:
"The pipeline view organizes leads into stage-based state buckets. When a lead is 
dragged and dropped into another column:
  1. The frontend immediately updates local state optimistically for instant visual 
     responsiveness.
  2. An asynchronous `PATCH /api/leads/:id/` call is dispatched to update the backend.
  3. If the backend rejects the change (e.g., transition requires a mandatory lost 
     reason or the rep lacks permissions), the UI reverts the card to its original 
     column and displays an error toast.
This gives users an instantaneous UI while maintaining absolute backend authority."

PART 5: ARTIFICIAL INTELLIGENCE, MULTIMODAL LLMS & PROMPT ENGINEERING
================================================================================

Q5.1: "How is multimodal speech-to-text implemented in your CRM without third-party 
      transcription services like Whisper or AssemblyAI?"
---------------------------------------------------------------------------------
Model Answer:
"I utilized Google Gemini's native multimodal audio capabilities (`gemini-2.5-flash`).
Rather than chaining multiple vendors (e.g. paying for speech-to-text, then paying 
again for an LLM summary), audio binary bytes (`audio/webm`, `audio/mp3`, `audio/wav`) 
are packaged directly into the SDK's `types.Part.from_bytes()` payload.
Gemini transcribes the dialogue verbatim with speaker labels in a single unified API 
call, dramatically cutting latency, architecture complexity, and API costs."

Q5.2: "How do you guarantee that the LLM returns valid JSON matching your schema?"
---------------------------------------------------------------------------------
Model Answer:
"Three levels of enforcement:
  1. SDK Configuration: Set `response_mime_type='application/json'` in Gemini's 
     `GenerateContentConfig`, instructing the model at the decoding level to emit 
     syntactically valid JSON.
  2. Temperature: Lowered to `0.2` for summarization to suppress speculative tokens.
  3. Defensive Sanitizer (`_clean_json_response`): Strips potential markdown 
     code fences (` ```json `), and employs a regex fallback 
     (`re.search(r'\{.*\}', text, re.DOTALL)`) to extract JSON objects if extraneous 
     tokens are present before parsing with `json.loads()`."

Q5.3: "Why did you implement a confirmation protocol for AI actions instead of 
      letting the LLM execute tool calls directly?"
------------------------------------------------------------------------------
Model Answer:
"Allowing an LLM autonomous write access to an enterprise database introduces 
severe risks: prompt injection attacks, accidental status regressions, or unverified 
data corruption.
My architecture enforces a **Human-in-the-Loop Safe Action Protocol**:
  - Read actions (summaries, overdue inspection) are answered immediately.
  - Write actions (e.g., 'Move Acme Corp to Won') are detected as mutation proposals.
  - The backend returns an `action_payload` with `action_required: true`.
  - The user must explicitly inspect the proposed change and click **[Confirm Action]**.
  - The action is then sent to a dedicated endpoint (`/api/ai/execute-action/`) where 
    standard RBAC permissions and audit logging are strictly enforced."

Q5.4: "How does your system handle AI outages or rate limits?"
--------------------------------------------------------------
Model Answer:
"Resilience by design: `ChatbotService` wraps external AI calls in a `try...except` 
block catching `AIProviderException`.
If Gemini encounters a rate limit (HTTP 429), network timeout, or missing API key, 
it seamlessly routes execution to `_generate_direct_crm_response()`.
This fallback computes 100% factual answers directly from Django ORM QuerySets 
(e.g., querying overdue follow-ups or pipeline totals directly). The user receives 
an immediate, accurate answer without any system crash."

PART 6: SYSTEM DESIGN, SCALABILITY & MICROSERVICES (FASTAPI)
================================================================================

Q6.1: "Why did you introduce a FastAPI microservice alongside Django?"
----------------------------------------------------------------------
Model Answer:
"In an enterprise CRM, read queries (global search, autocomplete) vastly outnumber 
write transactions. 
  - Django is optimized for robust business logic, complex ORM models, and ACID writes.
  - FastAPI is an asynchronous, high-concurrency framework built on Starlette and 
    Pydantic, ideal for ultra-fast, read-only I/O workloads.
By offloading global search across leads and customers to FastAPI (port 8001), 
search latency dropped to sub-10ms, and heavy user searching never consumes 
Django's WSGI worker pool."

Q6.2: "How would you scale this application to support 50,000 concurrent sales reps?"
-------------------------------------------------------------------------------------
Model Answer:
  1. Database Scaling:
     - Implement PostgreSQL Primary-Replica architecture: Writes route to Primary, 
       read queries (dashboard, reporting, search) route to Read Replicas.
     - Connection Pooling: Use PgBouncer to manage thousands of client connections.
  2. Caching Layer:
     - Deploy Redis for caching static lists (lead stages, lead sources) and 
       frequent KPI metrics with cache invalidation on lead mutation.
  3. Asynchronous Task Processing:
     - Offload audio transcription, CSV report generation, and automated follow-up 
       alert emails to Celery workers with a Redis/RabbitMQ message broker.
  4. Containerization & Orchestration:
     - Containerize backend and frontend via Docker; orchestrate with Kubernetes 
       (HPA - Horizontal Pod Autoscaler) behind an Nginx or AWS ALB load balancer.

PART 7: SECURITY, AUTHENTICATION & ROLE-BASED ACCESS CONTROL (RBAC)
================================================================================

Q7.1: "What is Insecure Direct Object Reference (IDOR) and how did you prevent it?"
-----------------------------------------------------------------------------------
Model Answer:
"IDOR occurs when an application exposes a reference to an internal database 
object (like `/api/leads/45/`) and fails to verify whether the requesting user 
has authorization to access that object.
In CRM Lite, IDOR is prevented in `LeadViewSet.get_queryset()`:
```python
if user.role not in ['ADMIN', 'MANAGER']:
    return Lead.objects.filter(Q(assigned_to=user) | Q(created_by=user))
```
If Sales Executive 'A' guesses the ID of Sales Executive 'B's lead, the ORM 
filters out the record before the view executes, returning `404 Not Found`. 
The executive cannot read, edit, or delete another rep's data."

Q7.2: "How do you protect against Cross-Site Scripting (XSS) and SQL Injection?"
-------------------------------------------------------------------------------
Model Answer:
  - SQL Injection: All database queries in Django strictly utilize the ORM's 
    parameterized queries. In the FastAPI microservice, queries use parameterized 
    placeholders (`?`), never raw string formatting (`f"SELECT ... {query}"`).
  - XSS Protection: React automatically escapes content rendered in JSX (e.g. 
    `{lead.name}`). We strictly avoid `dangerouslySetInnerHTML`.
  - HTTP Security Headers: In production, configure Content Security Policy (CSP), 
    `X-Content-Type-Options: nosniff`, and `X-Frame-Options: DENY` via Django middleware.

PART 8: REAL-WORLD SCENARIOS, BUG DEBUGGING & BEHAVIORAL QUESTIONS

Q8.1: "Describe a challenging bug you encountered in this project and how you solved it."
-----------------------------------------------------------------------------------------
Model Answer:
"A critical bug occurred during early customer conversion testing: when a lead 
was converted, occasionally the Customer profile was created, but an unhandled 
exception in the activity logging service crashed the request before updating 
the lead's status to `WON`.
This resulted in an orphaned Customer record while the Lead remained in `QUALIFIED` 
state, allowing the rep to click convert again and cause a duplicate key crash.

I resolved this by:
  1. Wrapping the entire operation inside `django.db.transaction.atomic()`.
  2. Adding a `OneToOneField` unique constraint on `Customer.lead` with `on_delete=models.PROTECT`.
  3. Adding pre-conversion status validation (`if lead.status == 'WON': raise ValidationError()`).
  4. Writing automated regression tests in `leads/tests.py` that intentionally 
     simulate a mid-conversion failure to verify that the entire database state 
     rolls back cleanly."
